## Contexto del producto

La aplicación permite vincular **recuerdos digitales a objetos físicos**.

Un usuario puede:

1. Crear una cuenta.
2. Crear un recuerdo.
3. Añadir fotografías, vídeos, audios, texto, fecha y ubicación opcional.
4. Registrar un objeto físico mediante una o varias fotografías.
5. Más adelante abrir una cámara de escaneo.
6. Apuntar al objeto.
7. El sistema reconoce cuál de los objetos previamente registrados es.
8. Abre automáticamente el recuerdo digital asociado.
9. Los recuerdos pueden compartirse con otros usuarios mediante permisos.
10. Un objeto solo debe buscar coincidencias dentro de los objetos pertenecientes al usuario o compartidos con él.

NO estamos intentando construir un Google Lens capaz de identificar cualquier objeto del mundo.

El problema es mucho más concreto:

> Dada una imagen capturada ahora, determinar cuál de los objetos previamente registrados y accesibles para este usuario es el candidato más parecido.

El reconocimiento visual sirve para navegar hasta el recuerdo. **Nunca debe utilizarse como sistema de autenticación o contraseña.**

## MUY IMPORTANTE: reconocimiento visual

Analiza específicamente el sistema de reconocimiento existente.

No asumas que Python debe eliminarse.

Determina qué estrategia utiliza actualmente y evalúa cuál de estas arquitecturas es más adecuada:

### Opción A — Todo en Next.js / TypeScript

Utilizar JavaScript/TypeScript si el reconocimiento actual puede implementarse de forma robusta mediante:

* ONNX Runtime
* TensorFlow.js
* APIs adecuadas
* procesamiento compatible con Node
* inferencia en navegador
* WebAssembly/WebGPU

### Opción B — Next.js + microservicio Python

Si Python ofrece una ventaja clara para OpenCV, PyTorch, transformers, embeddings u otras herramientas de visión artificial:

Mantén el reconocimiento como un servicio independiente y pequeño.

Ejemplo conceptual:

Next.js
→ envía imagen/frame
→ API Python
→ procesa imagen
→ genera descriptor/embedding
→ compara candidatos autorizados
→ devuelve:

```ts
{
  status: "match" | "ambiguous" | "no_match",
  objectId?: string,
  confidence?: number,
  alternatives?: []
}
```

El frontend nunca debe conocer detalles internos innecesarios del modelo.

Python debe quedar aislado detrás de una API clara.

Puedes utilizar FastAPI si es apropiado.

### Opción C — Arquitectura híbrida

Si tiene sentido:

* preprocesado en cliente;
* inferencia local;
* búsqueda vectorial en backend;
* Python solamente para entrenamiento/testing/PoC.

Elige la solución según el código que YA existe y las necesidades reales.

No conserves Python simplemente porque ya exista.

Pero tampoco reescribas funcionalidad de visión artificial estable en JavaScript sin una razón técnica.

## Flujo de reconocimiento deseado

Registro:

```text
Usuario
→ Crear recuerdo
→ Vincular objeto
→ Capturar 1-4 imágenes
→ procesar referencias
→ generar características / embeddings
→ guardar referencias
→ asociarlas al object_id
```

Escaneo:

```text
Usuario
→ Scan
→ cámara
→ obtener frame adecuado
→ procesar imagen
→ generar representación visual
→ buscar SOLO dentro de objetos autorizados
→ calcular similitud
→ MATCH / AMBIGUOUS / NO MATCH
```

Resultado:

### MATCH

Abrir recuerdo directamente.

### AMBIGUOUS

Mostrar 2-3 candidatos.

### NO MATCH

Informar de que no se reconoce el objeto y permitir repetir el escaneo.

## Privacidad y seguridad

La arquitectura debe asumir desde el principio:

* recuerdos privados por defecto;
* autenticación obligatoria para contenido privado;
* owner/editor/viewer;
* RLS si utilizamos Supabase;
* Storage protegido;
* URLs firmadas cuando proceda;
* nunca confiar en datos enviados desde el cliente para decidir permisos;
* filtrar objetos autorizados ANTES de devolver resultados;
* no guardar secretos en frontend;
* validar uploads;
* limitar tamaño/tipo de archivos;
* no utilizar reconocimiento facial.
